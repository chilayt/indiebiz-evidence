# 维护协作协议

> 2026-11-10 与 Codex 讨论后定稿。适用于"Codex 出方案/补丁，lead 落盘、验证、push"的分工。

## 一、每轮任务卡

每轮开始前给出一张任务卡，包含：

- **基线 SHA**（补丁必须对应它）
- **单一目标**（一个可独立提交的行为变化，约 1–3 个手写文件）
- **允许修改的文件**（明确列出，其余不动）
- **禁止事项**
- **验收条件**

迁移、接口调整、检测规则**分开交付**，不混在一张卡里。

## 二、Codex 的产出格式

**unified diff**，对应明确基线 SHA，附：

1. 变更理由
2. 验证命令与预期退出码 / 关键结果
3. 兼容性影响
4. 撤回方式

行号用于导航，**补丁是应用依据**。

## 三、lead 的职责

1. `git apply --check` 先验；基线变了或补丁不匹配 → 退回重出
2. 落盘、跑 `scripts/run_release_gate.py`、审查最终 diff
3. commit / push
4. Codex 未经明确指令不执行这些动作

## 四、直接驳回的情形

- 无法验证的断言
- 超出任务范围 / 额外重构
- **修改预期以迎合当前输出**
- 吞掉失败、把"未运行"写成"通过"
- 隐含破坏接口或数据、缺少必要迁移或恢复办法

驳回时指出**具体 hunk 和失败判据**。

## 五、分歧怎么裁决

| 类型 | 裁决依据 |
|---|---|
| 行为事实 | 固定输入 + 公开契约 + 可复现结果 |
| 契约本身含糊 | 先明确契约，再判行为 |
| 范围、优先级、可接受取舍 | **lead 拍板** |
| 证据缺失 | 保留"未知"，任何一方都不能宣布成立 |

## 六、验证状态分级

写清属于哪一级：**未运行 / 本地通过 / CI 通过 / 人工验收**。

失败保留退出码与最小日志。**已知失败不能靠 skip、放宽断言或删样例变绿。**

## 七、每轮交接记录

lead 记录：任务编号、前后 SHA、补丁摘要、接受的语义决定、验证命令与结果、遗留失败、下一步。

下一轮先读交接记录和对应 diff；**只有出现矛盾才扩大阅读范围**。

## 八、停损（建议值，不是考核）

- 一个补丁目标在 30–60 分钟内可审阅
- 单条验证命令预设超时
- 连续两次同因失败 → 换方法或交出阻断证据

墙钟时间与 CPU 时间只能说明等待多，不能单独判断原因。
